# Backend C API coverage

triton-ng wraps `tritonbackend.h` and the `TRITONSERVER_*` functions a backend calls. This page
says what is wrapped and what is not. The headers are the ones of the release in
[`.gitmodules`](https://github.com/rdcm/triton-ng/blob/main/.gitmodules) (`r25.09`, backend API
1.19).

## What the backend exports

`nm -D --defined-only target/release/libtriton_custom_backend.so` lists the entry points Triton
looks up in the library; the example backend exports these eight:

| Symbol | Generated by |
|---|---|
| `TRITONBACKEND_Initialize`, `TRITONBACKEND_Finalize` | `#[triton_ng::backend]`, `CustomBackend` |
| `TRITONBACKEND_GetBackendAttribute` | `#[triton_ng::backend]`, `CustomBackend::attributes` |
| `TRITONBACKEND_ModelInitialize`, `TRITONBACKEND_ModelFinalize` | `#[triton_ng::backend]`, `CustomBackend` |
| `TRITONBACKEND_ModelInstanceInitialize`, `TRITONBACKEND_ModelInstanceFinalize`, `TRITONBACKEND_ModelInstanceExecute` | `#[triton_ng::backend]`, `CustomBackend` |

`TRITONBACKEND_ApiVersion` is a function of the server, not of the backend: a backend calls it and
is not allowed to export it. Triton resolves the symbols of a library when it loads it, so a
library built against these headers does not load on a server that predates one of them: on
`24.02-py3` the load fails with `undefined symbol: TRITONSERVER_MetricArgsNew` before any backend
code runs.

## Not wrapped

Absent from the tree; the C functions are named so that they can be compared against the headers.

| Area | Functions | What a backend cannot do |
|---|---|---|
| Response statistics | `TRITONBACKEND_ModelInstanceReportResponseStatistics`, `TRITONBACKEND_ModelInstanceResponseStatistics*` | Fill `response_stats` of the model statistics, which reports per-response compute output times |
| Trace activities | `TRITONSERVER_InferenceTraceReportActivity` | Add a custom activity to the trace of a request |
| Sequences and state | `TRITONBACKEND_StateNew`, `TRITONBACKEND_StateUpdate`, `TRITONBACKEND_StateBuffer*` | Serve `sequence_batching` models with state of their own |
| Custom batching | `TRITONBACKEND_ModelBatcherInitialize`/`Finalize`, `TRITONBACKEND_ModelBatchInitialize`/`Finalize`/`IncludeRequest` | Decide itself which requests form a batch |
| Host policy | `TRITONBACKEND_InputPropertiesForHostPolicy`, `TRITONBACKEND_InputBufferForHostPolicy` | Read the inputs Triton keeps for the host policy of an instance |
| Buffers of a response and an input | `TRITONBACKEND_InputBufferAttributes`, `TRITONBACKEND_OutputBufferAttributes`, `TRITONBACKEND_InferenceResponseOutput`, `TRITONBACKEND_InferenceResponseOutputByName`, `TRITONBACKEND_RequestInputByIndex` | Read a buffer with its attributes of a response, or an input by index |
| BLS request mutation | `TRITONSERVER_InferenceRequestRemoveInput`, `TRITONSERVER_InferenceRequestRemoveRequestedOutput`, `TRITONSERVER_InferenceRequestAppendInputDataWithHostPolicy` | Take an input or an output back from a BLS request, or append host-policy data |

The decoupled path of Triton (`TRITONBACKEND_ResponseFactoryNew`, `...SendFlags`) is wrapped;
`TRITONBACKEND_ResponseNewFromFactory` and `TRITONBACKEND_ResponseFactoryIsCancelled` are not
used, the cancellation of a decoupled request comes back through `ResponseSender::is_cancelled`.

## Reproducing

```bash
make build            # target/release/libtriton_custom_backend.so
make download-model   # the MNIST models, once
make docker-env-up    # Triton 25.09-py3 with that .so and models/
make tests            # the unit tests and the tests against that server
make docker-env-down
```
