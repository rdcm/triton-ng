# Triton C API coverage

A function-by-function comparison of **all 276 exported function declarations** in
`tritonbackend.h` (104) and `tritonserver.h` (172), including backend entry points.
The baseline is **Triton r25.09 / backend API 1.19**. Types, enums, constants and callback
function-pointer typedefs are defined in the linked headers, but are not separate function rows.

`+` means the SDK/backend implements or uses this exact C function; `−` means it does not.
An alternative implementation is described explicitly and does not turn a `−` into a `+`.

The tables keep **one row per C function**, grouped by header and purpose. Links in
the first column open the declaration; links in the SDK columns open implementation evidence.
`internal` means implementation support, **not a public API for Python model authors**;
`(helper)` means a call through the shared Triton backend utilities on a path used by Python.
Rust RAII cleanup and bookkeeping also count as implementation, even without a public raw method.
Raw generated declarations in `triton-ng-sys` alone do **not** count as safe SDK coverage.

For example, `TRITONBACKEND_GetBackendAttribute` is **implemented by both projects**:
Rust generates it with `#[triton_ng::backend]` and exposes `CustomBackend::attributes`;
Python implements it in C++ without an equivalent Python model hook.

This is C API coverage, not a comparison of network clients: `triton-ng-client` and
`tritonclient` use gRPC/HTTP rather than these C functions. Server creation and command-line
configuration belong to the hosting process; their absence from a backend SDK is intentional.
For user-facing feature tradeoffs, see [Python comparison](https://github.com/rdcm/triton-ng/blob/main/docs/python_backend.md).

## Source baseline

- Core headers: [r25.09 at `564a324`](https://github.com/triton-inference-server/core/tree/564a324ecdde071c7a2493cc128db8e34a68d290/include/triton/core), matching `deps/triton-core` and the vendored SDK headers.
- Rust: triton-ng 0.4.0 API; [release boundaries](https://github.com/rdcm/triton-ng/blob/main/CHANGELOG.md).
- Python backend: [r25.09 at `8b5a055`](https://github.com/triton-inference-server/python_backend/tree/8b5a055e6f2cdd22cf6d3644e5822b01ffc62ce1/src).
- Shared C++ backend utilities: [r25.09 at `5fa6450`](https://github.com/triton-inference-server/backend/tree/5fa645030c0e725c4ac546e064207fc572e940fa). Only helper paths used by Python are counted, not every function in that library.

## Not wrapped

There are eight `tritonbackend.h` entry points without a direct safe Rust wrapper:
input/output buffer attributes, input-by-index, requested output-buffer properties,
factory cancellation, response creation from a factory, and the two `TRITONBACKEND_InferenceResponseOutput*`
helpers. Some have alternatives: Rust uses named inputs and retains the original request for
streaming responses and cancellation. The tables distinguish those alternatives from missing capabilities.

`TRITONBACKEND_ModelInstances` is not a function in these headers. A custom Python `is_ready`
hook from newer releases is not part of this r25.09 comparison.

## Verification and limitations

For this audit, the inventory was matched against declarations in both vendored headers, including both
`TRITONBACKEND_DECLSPEC` and `TRITONBACKEND_ISPEC`. Implementation status is based on Rust
source, Python r25.09 C++/Python source, and the shared backend helper call paths. A `+` does
not imply every combination of datatype, device, callback timing or failure mode is tested.

`make doc` checks documentation warnings; `make build` compiles the SDK, examples and guide
snippets; `make tests` exercises the unit and integration suite against `make docker-env-up`.
Those checks do not execute Python conformance tests or prove every row at runtime.
The [guides](https://github.com/rdcm/triton-ng/blob/main/docs/README.md) document ownership,
GPU, tracing and r25.09 limitations for the supported Rust paths.
