# triton-ng

[![crates.io](https://img.shields.io/crates/v/triton-ng.svg)](https://crates.io/crates/triton-ng)
[![docs.rs](https://img.shields.io/docsrs/triton-ng)](https://docs.rs/triton-ng)

Rust SDK for [NVIDIA Triton Inference Server](https://github.com/triton-inference-server/server).

Provides two things:
- A safe Rust API for writing **custom Triton backends** (compiled as `.so` and loaded by Triton)
- A high-level async **gRPC client** for sending inference requests to a running Triton server

See [CHANGELOG.md](https://github.com/rdcm/triton-ng/blob/main/CHANGELOG.md) for release history.

## Crates

| Crate | Description |
|---|---|
| `triton-ng-sys` | Raw FFI bindings generated by bindgen from `tritonbackend.h` |
| `triton-ng` | Safe Rust wrapper over `triton-ng-sys` |
| `triton-ng-macros` | Proc-macros for `triton-ng` |
| `triton-ng-client` | High-level async gRPC client |
| `example/custom-backend` | Example custom backend (MNIST, proxies to ONNX model) |
| `example/app` | Example client application |
| `benches` | Benchmarks against python_backend: the bench backend, the models of both backends, the `perf_analyzer` driver |

## Writing a custom backend

Implement the `CustomBackend` trait and register it with `#[triton_ng::backend]`:

```rust ignore
use triton_ng::{CustomBackend, Context, DataType, Error, InferenceRequest, Request, Response};

struct MyBackend;

#[triton_ng::backend]
impl CustomBackend for MyBackend {
    async fn model_instance_execute(ctx: Context, requests: Vec<Request>) -> Result<(), Error> {
        for request in requests {
            let data = request.get_input("INPUT")?.as_bytes()?;

            let mut inference = InferenceRequest::new(ctx.server(), "my_model", -1)?;
            inference.add_input_with_data("INPUT", DataType::Fp32, &[1, 10], data)?;
            inference.add_requested_output("OUTPUT")?;
            let result = match ctx.server().infer_async(inference).await {
                Ok(result) => result,
                Err(e) => {
                    request.respond_error_with_code(e.code(), &e.to_string())?;
                    continue;
                }
            };

            let mut response = Response::new(request)?;
            response
                .create_output("OUTPUT", DataType::Fp32, &[1, 10])?
                .write_fp32_vec(&result.output("OUTPUT")?.as_fp32_vec()?)?;
            response.send()?;
        }
        Ok(())
    }
}
```

Build as a `cdylib`:

```toml
# Cargo.toml
[lib]
crate-type = ["cdylib"]

[dependencies]
triton-ng = "0.3.0"
```

Or the latest code from the repository:

```toml
[dependencies]
triton-ng = { git = "https://github.com/rdcm/triton-ng.git" }
```

A batch (`requests`) is what Triton's dynamic batcher collected; the future runs to its end on
the Triton thread of the instance, so Triton forms the next batch meanwhile and batches of a
model run in parallel on its instances (`instance_group` count). Inside the batch, several BLS
calls awaited together run at the same time.

The API reference is on [docs.rs](https://docs.rs/triton-ng), with these guides under its `docs` module.

See [Batching and concurrency](https://github.com/rdcm/triton-ng/blob/main/docs/batching_and_concurrency.md) for how Triton forms
batches, what to tune and the measurements behind this execution model, [Execution model and thread safety](https://github.com/rdcm/triton-ng/blob/main/docs/execution_model_and_thread_safety.md) for instances
and how their batches run, request ownership,
error codes, BLS futures, threads, cancellation, shutdown and batching,
[Request metadata and tracing](https://github.com/rdcm/triton-ng/blob/main/docs/request_metadata_and_tracing.md) for request IDs, sequences and
BLS calls in Triton traces, [Streaming](https://github.com/rdcm/triton-ng/blob/main/docs/streaming.md) for decoupled models that answer with a
stream of responses and for reading such streams over BLS, [Memory buffers](https://github.com/rdcm/triton-ng/blob/main/docs/memory_buffers.md)
for BLS inputs and outputs in pinned and GPU memory and for passing inputs of a request on to BLS
calls without a copy, [Metrics](https://github.com/rdcm/triton-ng/blob/main/docs/metrics.md) for backend
metrics on Triton's Prometheus endpoint, and
[Model management and configuration](https://github.com/rdcm/triton-ng/blob/main/docs/model_management_and_configuration.md) for the backend
config and attributes, completing model configs, loading models from a backend and
rescheduling requests, and [Benchmarks](https://github.com/rdcm/triton-ng/blob/main/docs/benchmarks.md) for the measurements against python_backend. The [documentation index](https://github.com/rdcm/triton-ng/blob/main/docs/README.md) lists every section.

## Using the gRPC client

```rust ignore
use triton_ng_client::{InferInput, InferOptions, TritonClient, TritonClientConfig};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let client = TritonClient::new(TritonClientConfig::new("http://localhost:8001")).await?;

    let meta = client.model_metadata("my_model", None, None).await?;
    let n: usize = meta.inputs[0].shape.iter().map(|&d| d as usize).product();

    let response = client
        .infer(
            "my_model",
            None,
            [InferInput::fp32("INPUT", meta.inputs[0].shape.clone(), vec![0.0f32; n])],
            ["OUTPUT"],
            InferOptions::default(),
        )
        .await?;

    println!("{:?}", response.outputs[0].data);
    Ok(())
}
```

Streaming responses of a decoupled model over gRPC `ModelStreamInfer`:

```rust ignore
let mut stream = client
    .infer_stream("my_stream_model", None, inputs, ["TOKEN"], InferOptions::default())
    .await?;
while let Some(response) = stream.next().await {
    println!("{:?}", response?.outputs[0].data);
}
```

Dropping the stream cancels the request.

TLS:

```rust ignore
use triton_ng_client::{ClientTlsConfig, TritonClientConfig};

let config = TritonClientConfig::new("https://triton.example.com:8001")
    .with_tls(ClientTlsConfig::new()); // uses system roots
```

## Comparison with python_backend

[python_backend](https://github.com/triton-inference-server/python_backend) is NVIDIA's backend for
models written in Python, and the usual way to write BLS orchestration around framework models.
triton-ng covers the same ground from Rust. What matches and what differs, as of triton-ng 0.3.0
and python_backend r25.09:

| | python_backend | triton-ng |
|---|---|---|
| Runs | a Python stub process per instance; every batch, tensor and BLS call crosses to it through shared memory | in the Triton process: a `.so` that calls the C API |
| `execute` | `def` or `async def`; the batches of an instance run one after another | `async fn`; the batch future runs on the Triton thread of its instance, BLS calls awaited together run at once |
| BLS | `exec()`; `async_exec()` is the blocking `exec` on asyncio's thread pool | `Server::infer_async`, a future woken by Triton's response callback |
| BLS to a decoupled model | `exec(decoupled=True)`, an iterator | `Server::infer_stream`, a `Stream` |
| Cancelling a BLS call | `iterator.cancel()` | `stream.cancel()`, or dropping the future or the stream |
| Decoupled models | `get_response_sender()`, `send(flags=FINAL)` | `Request::into_sender`; the types enforce exactly one final flag |
| Request metadata | id, correlation id, flags, timeout, parameters as JSON | the same, typed, one parameter at a time |
| BLS request metadata | id, correlation id, flags, timeout, parameters, trace | the same, plus priority and `f64` parameters |
| Errors | `TritonError(message, code)` | `respond_error_with_code`; the code of a failed BLS call is passed on |
| Rescheduling | `set_release_flags(RESCHEDULE)` | `Request::reschedule`, with the checks r25.09 does not make |
| Metrics, statistics | `MetricFamily`; statistics reported by the C++ side | `CounterFamily`, `GaugeFamily`, `HistogramFamily`; statistics reported by triton-ng |
| Model loading, `auto_complete_config` | `pb_utils.load_model`, `ModelConfig` | `Server::load_model`, `AutoCompleteConfig` |
| Backend config and attributes | not exposed | `Backend::config`, `CustomBackend::attributes` |
| Memory | numpy arrays; CPU tensors copied into shared memory, GPU tensors through DLPack and CUDA IPC | RAM, pinned and GPU buffers of Triton's memory manager; BLS outputs taken over and request inputs passed on without a copy |
| Data types | any numpy dtype | fp32, fp64, i32, i64, u64, bool, strings and raw bytes |
| GPU outputs of a response, GPU inputs read on the CPU | yes, copied | no: triton-ng has no CUDA runtime |
| `is_ready` | yes | no, needs r26.04 |
| PyTorch, TensorFlow, JAX inside the model | yes | no: the model goes to its framework backend and is called over BLS |
| A crash in the model | takes down the stub; Triton notices | panics are caught at the FFI boundary; a segfault takes down Triton |

## Benchmarks

python_backend and triton-ng on the same five BLS workloads, measured with `perf_analyzer`:
requests per second and latency at concurrency 1, 4, 16 and 64, both backends in one Triton,
two CPU instances each, the MNIST ONNX model as the BLS target. `make benchmarks` runs them,
the tables are its output; [Benchmarks](https://github.com/rdcm/triton-ng/blob/main/docs/benchmarks.md) describes the method, the models, the
environment and what the numbers mean.

- CPU: AMD Ryzen 9 9950X3D 16-Core Processor, 32 threads
- RAM: 30 GiB
- GPU: NVIDIA GeForce RTX 5080, 580.178.04 (not used by the benchmark models)
- OS: Linux-7.2.15-100.fc43.x86_64-x86_64-with-glibc2.42
- Triton: 2.61.0 (nvcr.io/nvidia/tritonserver:25.09-py3)
- perf_analyzer: Perf Analyzer Version 0.0.0 (commit 3a49a23)
- Concurrency: 1, 4, 16, 64; measurement window 5000 ms, stability 10 %

## Getting started

### Prerequisites

- Rust 1.99.0, pinned in `rust-toolchain.toml` (rustup installs it on the first build)
- NVIDIA driver 570+ (580+ for Blackwell / RTX 50xx)
- [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html)
- Docker

### First run

```bash
make build           # compile custom backend → target/release/libtriton_custom_backend.so
make download-model  # download mnist_onnx + create model version dirs
make docker-env-up   # start Triton (mounts .so and models/)
```

### Run the example app

```bash
cargo run --manifest-path=example/app/Cargo.toml --release
```

Triton must be running with the example models in READY state.

The Triton headers are vendored in `triton-ng-sys/include`, so the submodules in `deps/` are not
needed to build. `make update-submodules` refreshes them and the headers from the Triton release
branch named in `.gitmodules` (`r25.09`, matching the `tritonserver:25.09` image).

### Run integration tests

```bash
make tests           # cargo nextest run --workspace
```

Tests require a running Triton instance (`make docker-env-up`). The tracing tests read the traces
Triton writes into `target/traces`.

### Check the documentation

```bash
make doc             # rustdoc for the workspace, as docs.rs builds it; warnings are errors
```

Every public item is documented (`#![deny(missing_docs)]`), the README and the guides in
`docs/` are part of the crate documentation.

### Rebuild after backend changes

```bash
make build
make docker-env-down && make docker-env-up
```
